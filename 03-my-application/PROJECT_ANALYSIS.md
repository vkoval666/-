# Реальный проект: ERP / ComplexOS

Этот документ связывает теорию из подготовки с реальным кодом из релиза `erp-release-6009`.

## Что видно из проекта

Проект представляет собой не одно небольшое приложение, а набор связанных компонентов. В архиве есть, среди прочего:

- `complexos` — основной ComplexOS;
- `cm-drv` — драйвер кофемашины;
- `complexui` — UI;
- `front-erp` — фронтенд ERP;
- `mobile-api` — API мобильного приложения;
- `svc` — набор сервисов;
- `supervisor` и `watchdog` — инфраструктурные компоненты;
- `megadb` — работа с данными;
- `gw` — gateway;
- `lib` — библиотеки;
- systemd service-файлы и Docker-конфигурация.

Это хорошо показывает разницу между **приложением**, **сервисом** и **системой**.

## ComplexOS как пример консольного приложения

Точка входа `complexos/complexos.ts` запускает REPL с prompt `> `. При старте подключаются конфигурация, ERP, API, очередь задач, bus, менеджеры устройств, заказы, логи, watchdogs и другие компоненты.

То есть консоль здесь — только интерфейс взаимодействия. Основная логика вынесена в отдельные компоненты.

## Пример разделения ответственности

В `complexos/complexos.ts` отдельно подключаются:

- `createConfigManager` — работа с конфигурацией;
- `createDeviceManager` — управление устройствами;
- `createOrderProcessor` — обработка заказов;
- `createPreferencesManager` — пользовательские настройки;
- `makeQueueManager` — очередь;
- `createMediaManager` — медиаресурсы;
- `setupLogsAggregator` — агрегация логов;
- `setupTroubleshooter` — диагностика;
- `connectWatchdogs` — watchdogs.

Это реальный пример принципа **Single Responsibility**: разные задачи распределены между отдельными компонентами, а не сосредоточены в одном большом обработчике.

## Где здесь DI

В `complexos/complexos.ts` компоненты получают зависимости через параметры фабрик. Например, `createOrderProcessor` получает `bus`, `devices`, `erp`, `redis`, `operatingModeManager`, `preferencesManager`, `queueManager` и другие зависимости.

Это практический пример идеи Dependency Injection: компонент не обязан самостоятельно создавать все используемые им зависимости.

## Где здесь идеи Clean Architecture

Проект не следует какой-то одной «чистой» архитектуре в учебном виде целиком, но в нём видны её полезные принципы:

- отдельные компоненты имеют разные ответственности;
- бизнес-операции вынесены из точки входа;
- работа с устройствами отделена от управления заказами;
- внешние зависимости передаются компонентам;
- инфраструктурные детали находятся в отдельных модулях.

На оценке корректнее сказать: **я применяю принципы Clean Architecture, а не утверждаю, что весь проект буквально построен по каноническому шаблону Clean Architecture.**

## MVP / MVI применительно к проекту

MVP/MVI особенно естественно обсуждать на уровне UI. В `complexui` и `front-erp` есть пользовательский интерфейс, поэтому там логично разделять отображение, состояние и обработку пользовательских действий.

Для `ComplexOS` с REPL эти модели можно применять концептуально: ввод пользователя является событием/Intent, отдельная логика обрабатывает его, а результат возвращается интерфейсу.

## Resources

В проекте есть конфигурации, локализация, media и другие внешние данные. Например, `complexos` загружает OS config, products, supply data, avatars, backgrounds и media.

Это хороший практический пример того, почему данные и ресурсы не стоит смешивать с основной бизнес-логикой.

## Итог для оценки

Мой проект показывает, что я понимаю архитектуру не только теоретически. Я могу взять конкретный компонент, определить его ответственность, назвать его зависимости и объяснить, почему разделение компонентов упрощает поддержку и диагностику.
