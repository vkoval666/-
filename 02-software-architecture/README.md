# 2. Архитектура ПО

## Зачем нужна архитектура

Архитектура определяет, как разделены ответственности внутри приложения и как его части взаимодействуют между собой.

Хорошая архитектура помогает менять одну часть системы с минимальным влиянием на остальные, упрощает тестирование и поддержку.

## MVP

**Model — View — Presenter.**

- Model отвечает за данные и бизнес-логику.
- View отвечает за отображение и ввод пользователя.
- Presenter связывает View и Model и принимает решения о том, что View должна показать.

Для моего консольного приложения View — это консольный интерфейс: ввод команд и вывод результата. Presenter мог бы получать пользовательский ввод, вызывать нужную логику и передавать результат обратно в консоль.

## MVI

**Model — View — Intent.**

Пользовательское действие представляется как Intent. Система обрабатывает Intent и формирует новое состояние Model, которое отображается View.

Главная идея — иметь понятный поток: действие пользователя → обработка → новое состояние → отображение.

Для консольного приложения такой подход можно применять концептуально: команда пользователя является Intent, обработчик меняет состояние приложения, после чего консоль отображает актуальный результат.

## MVP и MVI: сходство и отличие

Обе архитектуры разделяют интерфейс и внутреннюю логику и уменьшают связанность компонентов.

В MVP основной акцент — на Presenter, который управляет взаимодействием View и Model. В MVI основной акцент — на однонаправленном потоке событий и состоянии приложения.

## Clean Architecture

Clean Architecture разделяет приложение на слои и старается направлять зависимости внутрь, к бизнес-правилам.

Главная идея: бизнес-логика не должна зависеть от конкретной базы данных, UI, файловой системы или внешнего сервиса.

Это позволяет заменить конкретную реализацию, не переписывая основную бизнес-логику.

## Resources

Resources — внешние по отношению к коду ресурсы приложения: например, строки, конфигурации, шаблоны или другие данные, которые не обязательно зашивать непосредственно в программную логику.

Вынос ресурсов отдельно делает код чище и позволяет менять данные без изменения самой логики.

## Dependency Injection (DI)

Dependency Injection — передача объекту его зависимостей извне вместо того, чтобы объект создавал их самостоятельно.

Например, вместо того чтобы сервис сам создавал конкретный файловый репозиторий, ему можно передать интерфейс репозитория.

Плюсы: слабая связанность, удобнее тестирование и проще заменять реализации.

## Как применяю в разработке

Если в моём консольном приложении есть бизнес-логика, ввод/вывод и работа с внешними ресурсами, я могу разделить их по ответственности. Интерфейс консоли не должен содержать всю бизнес-логику. Внешние зависимости лучше передавать через абстракции. Это позволяет менять способ хранения данных или конкретный сервис без переписывания основной логики.
